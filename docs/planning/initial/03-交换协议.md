# FFXIV 服装骨架 Blender 交换协议

建议将 glTF 2.0 用作骨骼变换与模型交换载体，将 sidecar JSON 用作骨骼身份、来源和游戏元数据的对照表。原始 SKLB 是游戏数据保真的基线。以下为待实现协议，开发阶段应根据未编辑往返结果冻结第一版。

## 项目目录

```text
clothing-project/
  project.json
  baseline/
    clothing-original.sklb
    skeleton-snapshot.json
    dependency-manifest.json
  exchange/
    skeleton.gltf
    skeleton.bin
    skeleton.ffxiv.json
    reference.gltf
    reference.bin
  blender/
    clothing.blend
  returned/
    revision-0001/
      edited.gltf
      edited.bin
      edited.ffxiv.json
      complete.json
  candidate/
    revision-0001/
      clothing.sklb
      validation.json
  deployment/
    deployment-plan.json
```

目录名称是设计建议。真实 MDL 等输入由依赖清单引用或保存在项目内；大型模型不必反复复制。选中的源文件哈希写入 project.json；游戏版本、国服 Dalamud 版本、Penumbra 版本、Blender 与插件版本一并记录。

返回版本只有在 glTF、bin 和 sidecar 都写完且哈希匹配后才生成 complete.json。文件监听只提示“发现新版本”，不自动转换、加载或安装。

## 字段的唯一权威来源

| 内容 | 权威来源 |
| --- | --- |
| 原始包装、未知字段、HKX 非编辑对象 | baseline 的原始 SKLB 和受信基线快照 |
| 原骨名称、原索引、LockTranslation 等保护属性 | 基线与导出 sidecar |
| 返回骨骼的位置、旋转与支持的缩放 | 返回 glTF，经 sidecar 身份映射后读取 |
| 新骨骼名称、身份、导出属性 | Blender 插件生成的返回 sidecar，并与 glTF 节点一致 |
| 参考骨与服装骨的边界 | 项目清单与 sidecar 的 ownerSkeleton 和 role |
| 新骨的游戏索引 | 插件端追加策略计算，Blender 不直接指定 |
| 最终目标路径、EST 和预览集合 | 插件面板当前部署计划 |

sidecar 不允许另一份“编辑后的 TRS”与 glTF 互相竞争。基线 TRS 可保存用于比对与恢复，不能覆盖明确发生的编辑。返回文件不能更改基线哈希或把其他项目的原骨冒充本项目骨骼。

## 骨骼身份

每根原骨获得稳定的项目 UUID，记录 ownerSkeleton、原始名称、原始索引、原父骨身份和角色。名称保留大小写；导出显示名称可以另设唯一 exportName。不同 skeleton 中同名骨骼不合并。

服装附加骨架中原有的公共锚点仍属于服装 skeleton，应保留原身份。另导出的基础参考 skeleton 即使有同名骨，也不能混入服装的候选 hkaSkeleton。

Blender 插件给新增骨分配新 UUID。复制骨骼可能同时复制自定义属性，插件需检测重复 UUID 并要求确认哪一根是新骨；不静默把原骨改成新骨。

原骨删除、重命名、重排、改父和改变受保护属性都阻断第一版回导。缺失原骨不能用新骨填补。新骨按稳定顺序追加，并保证新父先于新子；若原始模板本身采用其他布局，不对原骨自动拓扑重排，而应进入模板适配验证。

## glTF 中的骨骼识别

glTF skin.joints 是骨骼候选的明确列表。节点编号、文件数组排列和 Blender 内部顺序不能当作原始 SKLB 索引。关节列表与 sidecar UUID 对应后，再计算输出骨序。[glTF skin schema](https://github.com/KhronosGroup/glTF/blob/main/specification/2.0/schema/skin.schema.json)

骨架导出保留一个小型代理蒙皮网格，以承载 skin。Blender 配套插件将它放在独立集合中标记为代理，控制用户可见性，并在骨架导出时确保 skin 和所有关节仍存在。不能把代理网格导入成游戏服装的一部分。

普通 Blender 导出可能将未蒙皮或非变形骨转换为普通节点，或遗漏它们。第一版配套插件应显式构建或补齐返回的 skin.joints，并核实每根服装原骨及新增骨都在列表中。它可以保存 glTF extras 中的 UUID，但不能依赖通用导入器完整保存所有 bone custom properties。

推荐在插件导入时将身份写入 Blender 骨数据；返回导出完成后，以受控 exportName 对应节点，将 UUID 写入 extras，再写 sidecar。只在身份仍可唯一匹配时允许此步骤。出现无名节点、重复 exportName、丢失 UUID 或只剩普通节点时报告问题，不靠名称关键词猜测。

## Blender 编辑规则

基础参考骨架放到单独集合并锁定。服装附加骨架保留其原始锚点与姿态，新骨可在 Edit Mode 中建立层级。游戏输出只读取静止姿态，不把用户当前 Pose Mode 的视觉结果自动作为参考姿态。

IK、约束、控制骨、驱动器、Bendy Bones 和 Rigify 控制层不直接输出为游戏骨架。用于制作的控制骨应明确标记 editorOnly；用于蒙皮的自定义骨必须进入服装 skeleton。需要把姿态变为静止姿态时，后续增加单独的显式操作并重新校验依赖。

Armature 对象的平移、旋转和缩放第一版要求符合项目预设。用户改变对象变换时，先报告差异，再提供受控归一化操作；不能自动 Apply Transform 并假设不会影响网格绑定。

## 坐标与骨轴

内部统一采用明确约定的矩阵模型，例如数学上的列向量和父乘子。若 C# 使用 System.Numerics，需要在适配器中处理其 API 约定，不能直接把数学公式按存储顺序抄成实现。

父骨与子骨的世界静止矩阵为 Gp 和 Gi 时，子骨局部矩阵为 inverse(Gp) 乘 Gi。Blender 的 bone.matrix_local 表示相对 Armature 的骨矩阵，不能直接当作相对父骨的 Havok ReferencePose。实现依据实际 Blender API 校准。[Blender Armature 空间说明](https://developer.blender.org/docs/features/animation/armatures/)

项目记录唯一的坐标转换配置，包括轴向、手性、单位、四元数排列与矩阵约定。glTF 与 Blender 的坐标转换由一个指定模块执行；其余模块不得额外增加同样的轴旋转。FFXIV 到 glTF 的转换先按有效样本测定，不能只凭 Y up 或 Z up 硬编码一个看起来正确的旋转。

Blender 骨头、骨尾和 roll 的显示构造可能引入额外骨轴变换。导入时记录每根原骨的显示校正；回导时撤销校正，再恢复游戏姿态。不能根据子骨方向自动重算所有原骨朝向。骨尾缩短但方向不变，通常是显示编辑；骨头移动、roll 或方向变化则要纳入姿态差异。

未编辑往返时，在容差内未变化的原骨应复用原始 TRS 和保护字段。浮点清零、四元数转欧拉再转回、自动归一化骨轴等处理均不能默认执行。四元数 q 与负 q 应在比较中视为同一旋转。

Blender 原生 EditBone 不直接等价于带任意缩放的 Havok joint。第一版对新骨要求单位缩放；基线存在非单位或非均匀缩放时，应单独验证保真路径。无法准确表示的原骨允许保持原数据，但对其编辑进行阻断，不能用猜测缩放继续回写。矩阵分解出现 shear 或镜像时也阻断。

## 回导候选构造

1. 检查 projectId、源哈希、导出版本和返回 complete 文件。
2. 校验 glTF 引用与 sidecar 身份，得到服装 skeleton 的托管候选图。
3. 根据保护规则识别原骨与新骨。保持原索引，分配新增索引。
4. 计算局部姿态，验证有效 parent 图和数值可表示性。
5. 对照基线，列出所有索引引用结构，包括 wrapper 的连接与 layers、mapper、LocalFrames 和 Partitions 等。
6. 原引用保留；新增骨骼需要的列表或结构按已验证模板策略更新。存在无法判断的引用结构时停止构造。
7. 从原始文件载入插件私有 Havok 对象图，仅修改已支持字段。保留其他 NamedVariants、辅助 skeleton、float data 和未知可保留对象。
8. 保存新 HKX 并生成候选 SKLB。若包装字节完全不受编辑影响，保留原包装；需要修改已知引用或数据长度时重算偏移和填充。
9. 重新读取候选，比较骨数、姿态、层信息、mapper 和非编辑字段。通过后才进入服装依赖检查。

新增骨骼不自动加入所有 layers，也不自动映射到同名基础骨。模板策略必须定义如何处理 unmapped 骨骼、分区与其它相关数据；不能从一种模板推断所有骨架通用规则。

## Sidecar 草案字段

```json
{
  "schemaVersion": 1,
  "projectId": "项目 UUID",
  "exportRevision": 1,
  "baselineSha256": "原始 SKLB 的 SHA256",
  "ownerSkeleton": "clothing-top",
  "coordinateProfile": "由往返样例校准的配置 ID",
  "bones": [
    {
      "id": "骨骼 UUID",
      "role": "original",
      "exportName": "唯一显示名称",
      "originalName": "游戏原名称",
      "originalIndex": 0,
      "parentId": null,
      "protected": true,
      "lockTranslation": 0
    }
  ]
}
```

此 JSON 为字段示意，不是可部署项目。第一版还需加入文件哈希、骨架对象身份与模板策略版本。LockTranslation 的 0 仅作示例；真实原骨值从基线读取，新增骨默认值按模板明确设置。
