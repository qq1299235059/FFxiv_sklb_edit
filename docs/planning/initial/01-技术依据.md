# FFXIV 服装骨骼转换技术依据

SKLB 与 Blender 往返已有可参考实现，项目的主要难点是保留游戏专属数据，并让新增骨骼正确进入服装的加载、映射和蒙皮流程。格式转换可行性与当前国服版本兼容性需要分别验证。

## SKLB 与 Havok 的关系

SKLB 是 FFXIV 的骨架文件，包含游戏包装信息和 Havok 数据。Xande 的 `SklbFile` 将 HavokOffset 之前的字节作为 RawHeader 保留，再替换其后的 HKX；其 README 给出了 HKX 与 XML 双向转换示例。这说明可以以原始文件为模板编辑 Havok 内容，但简单拼接不足以覆盖全部游戏包装结构。[Xande 文件解析器](https://github.com/xivdev/Xande/blob/172423c87135f696be7a5f63672c594c84778286/Xande/Files/SklbFile.cs)，[Xande 使用说明](https://github.com/xivdev/Xande)

VFXEditor 的实现进一步读取两类包装布局，并处理头部、layers、填充与 HavokOffset。代码按 Version2 为 `0x3132` 或 `0x3133` 分流；实现时还要检查完整版本组合，不能据此把所有相似文件视为支持。新布局中出现 Bone Connect Index、Id 和 Parents。项目应保留原始头部字节、解析已知引用，并对未知版本拒绝写入。[SklbFile](https://github.com/0ceal0t/Dalamud-VFXEditor/blob/05f6eb0cce19a6a91ae275bce609299d573914b3/VFXEditor/Formats/SklbFormat/SklbFile.cs)，[SklbNewData](https://github.com/0ceal0t/Dalamud-VFXEditor/blob/05f6eb0cce19a6a91ae275bce609299d573914b3/VFXEditor/Formats/SklbFormat/Data/SklbNewData.cs)

Layers 也包含骨骼索引。保留原索引可以减少既有引用变化，但新增骨骼是否需要进入具体 layer，必须依据模板和游戏行为确定。[SklbLayer](https://github.com/0ceal0t/Dalamud-VFXEditor/blob/05f6eb0cce19a6a91ae275bce609299d573914b3/VFXEditor/Formats/SklbFormat/Layers/SklbLayer.cs)

Havok 骨架不只有名称、父子关系和静止姿态。`hkaSkeleton` 还包含 FloatSlots、ReferenceFloats、LocalFrames 和 Partitions，其中部分字段引用骨骼索引。不能把一个 HKX 容器全部重建成只有 bones 的简化文件。[FFXIVClientStructs hkaSkeleton](https://github.com/aers/FFXIVClientStructs/blob/main/FFXIVClientStructs/Havok/Animation/Rig/hkaSkeleton.cs)

## 已有 Blender 往返实现

VFXEditor 已提供骨架 GLTF 导出与导入。导出用 SharpGLTF 生成骨骼节点，并使用小型代理蒙皮网格承载 skin；导入读取节点变换，并尝试把同名骨骼放回原索引。项目可参考其转换路线，但应改用明确的骨骼身份表，不采用“节点名含 armature 或 mesh 就跳过”的判断，也不能用新骨骼填补丢失原骨骼的索引位置。[GltfSkeleton](https://github.com/0ceal0t/Dalamud-VFXEditor/blob/05f6eb0cce19a6a91ae275bce609299d573914b3/VFXEditor/Utils/Gltf/GltfSkeleton.cs)

VFXEditor 的 Blender 指南建议关闭 Guess Original Bind Pose，并选择适于回导的 Blender Bone Dir；导出选择 glTF Separate。它同时说明，FFXIV 骨架与 Blender 的骨长概念不同，骨骼长度不能直接作为游戏字段回写。这些设置源于旧版 Blender，第一版应由配套插件封装，并在实际 Blender 版本上重新验证。[VFXEditor Blender 指南](https://github.com/0ceal0t/Dalamud-VFXEditor/wiki/Using-Blender-to-Edit-Skeletons-and-Animations)

## 中间格式取舍

下表是针对本项目的工程判断。

| 方案 | 兼容性和工作量 | 数据保真问题 | 项目决策 |
| --- | --- | --- | --- |
| FBX | Blender 可处理，但 C# 往返还需额外库和适配；需核对具体库许可证 | 需要额外处理轴向、骨长、叶骨、节点变换和游戏元数据 | 第一版不实现 |
| glTF 2.0 | Blender 支持；VFXEditor 和 Penumbra 有可参考路线；SharpGLTF 可服务 C# 端 | 标准不表达 SKLB 包装和全部 Havok 对象，必须有配套元数据 | 主交换载体 |
| 专用 JSON 加 Blender 插件 | 自定义字段最直接，Python 与 C# 实现简单；普通导入器无法识别 | 骨骼与网格整合要自行完成 | 用于项目元数据与内部模型 |
| Havok XML | 适合调试和模板修改 | Blender 不直接提供本项目所需的可靠骨架编辑往返 | 内部诊断或转换桥 |
| BVH | 面向运动数据和简化层级 | 无法承载所需包装、映射和模型关联 | 不采用 |
| blend | 适合用户保存工作现场 | 插件端读取成本高，受 Blender 版本影响 | 编辑工程，不作回导协议 |

glTF 的 skin.joints 明确定义关节列表顺序；inverseBindMatrices 与该列表对应。但这种顺序不能直接当作 SKLB 原始索引，需要由元数据完成映射。[Khronos glTF 2.0 规范](https://github.com/KhronosGroup/glTF/blob/main/specification/2.0/Specification.adoc)

Penumbra 文档给出了 MDL 与 glTF 导入导出路径。因此第一版可使用它或用户已有模型工具完成网格回导，避免同期开发完整 MDL 编辑器。文档记载每 mesh 的骨骼映射表有 64 项限制；这是模型约束，不能误写成整个 SKLB 只能有 64 根骨骼。实际国服 MDL 版本仍需按解析器确认。[Penumbra Model IO](https://github.com/xivdev/Penumbra/wiki/Model-IO)

## 服装附加骨架与 EST

Penumbra 文档将 EST 定义为附加骨架选择配置，按装备、种族、性别和适用部位设置骨架 ID，并列出 face、head gear、chest gear 和 hair。针对服装，首版以 chest gear 的 top 附加骨架为样例，之后再研究头部装备。腿、手、脚和饰品不能直接照搬这个附加骨架流程。[Penumbra EST 文档](https://github.com/xivdev/Penumbra/wiki/Advanced-Editing#extra-skeleton-parematers-est)

建议把“服装选用哪个附加骨架”和“该骨架路径重定向到哪个本地文件”分成两个明确配置。沿用已有骨架 ID 的路径可能影响共享该 ID 的其他装备；使用另一个 ID 则必须确认 EST 解析、父骨架和资源加载都正确。第一版复用一套经过验证的模板，不任意生成新 ID。

## 附加骨架 mapper

VFXEditor 从 HKX 容器读取 `hkaSkeletonMapper`，并处理 SkeletonA、SkeletonB、SimpleMappings 和映射变换。名称相同只能作为候选关系，不能证明源骨架、目标骨架或变换已经正确。项目要区分静态 parent 层级、SKLB 包装连接信息和 Havok mapper。[SklbBones](https://github.com/0ceal0t/Dalamud-VFXEditor/blob/05f6eb0cce19a6a91ae275bce609299d573914b3/VFXEditor/Formats/SklbFormat/Bones/SklbBones.cs)，[SklbMapping](https://github.com/0ceal0t/Dalamud-VFXEditor/blob/05f6eb0cce19a6a91ae275bce609299d573914b3/VFXEditor/Formats/SklbFormat/Mapping/SklbMapping.cs)

本项目的待验证假设是：在已被正确加载、映射的附加骨架中，把自定义骨骼追加到有效父骨后，能够使绑定的小块测试网格随父骨运动。若模板依赖额外 unmapped 列表、分区或其他数据，需补齐这些结构后再验收。不能把该假设当作所有装备通用的结论。

## Havok 转换的运行位置

Xande 使用 FFXIV 客户端内置 Havok 函数，其 README 明确限定运行于 Dalamud 场景，并要求 HavokConverter 使用 Framework 线程。它最后核实的提交在 2024 年，适合作为技术参考，不能假设可直接编译进当前国服插件。[Xande 线程与使用说明](https://github.com/xivdev/Xande)

VFXEditor 的 HavokData 使用客户端类型注册表加载和保存 HKX，提供了较新的运行时适配参考。项目设计要求集中管理对象所有权、保存返回结果与释放顺序；对当前国服的签名和布局先做只读验证。[HavokData](https://github.com/0ceal0t/Dalamud-VFXEditor/blob/05f6eb0cce19a6a91ae275bce609299d573914b3/VFXEditor/Interop/Havok/HavokData.cs)

首版由插件内的专用运行时适配层完成 Havok 读取与写入。Blender 只编辑交换文件。独立离线 SKLB 编码器以后再评估，其实现难度不能按普通 JSON 转换估计。

## Penumbra API 能力边界

公开 API 提供路径解析、资源树、临时 Mod、临时集合、重绘、Mod 注册与重载。临时 Mod 的输入是游戏路径到文件或路径的字典，加打包后的 metadata manipulations；它不直接接收未经转换的 EST JSON。[API 仓库](https://github.com/Ottermandias/Penumbra.Api)，[临时 Mod 契约](https://github.com/Ottermandias/Penumbra.Api/blob/45749c89e80ab9f7a7a0557b9c87770980048051/Api/Temporary.cs)

已检查的 Editing API 暴露纹理转换；本规划不把界面上的 Model IO 功能当作现成的通用 MDL 转换 IPC。[Editing API](https://github.com/Ottermandias/Penumbra.Api/blob/45749c89e80ab9f7a7a0557b9c87770980048051/Api/Editing.cs)
